# 段階別計画

## レベル0: ツール制御・システムプロンプト・監視

### 現状と調査対象

`Test-LiveKit/agent.py`はツールとシステムプロンプトを登録し、セッション開始前に`setup_langfuse`を呼ぶ。
`observability.py`にはOTLP exporter、セッションID、終了時のflushがある。
既存テストは主に設定処理のモック検証であり、Langfuseへの実データ到着を保証しない。
ユーザー環境ではセッションは表示されるが、その中のtraceデータが見えないと報告されている。
原因は未確定であり、設定不足と断定しない。

### 実装・調査

1. span生成、親子関係、session IDとの対応、exporter送信、Langfuse受理、画面の絞り込みを順に確認する。
2. 実際に解決されたSDKバージョンと仕様を照合し、最小の実接続確認を用意する。
3. 正常終了だけでなく途中停止・例外・再接続時のflushと、セッション混線を検証する。
4. システムプロンプトをコードから分離し、Gitで版管理する。版番号をtraceに関連付ける。
5. LLMがツールを選び、承認が必要な操作は実行を保留する仕組みを設ける。
6. モデル名・プロバイダー・使用量・処理時間・エラーを記録する。

### 人の許可とツール実行

- 外部サービスへのツール操作は人の許可後に実行する。送信・更新・削除に加え、外部のメール取得やWeb検索も承認対象として扱う。
- ローカルの会話履歴参照、ローカルメモリ・ローカル文書検索は内部処理として扱う。
- 人へ操作対象と内容を示し、その内容に対する許可を得る。変更された宛先・本文・対象には以前の許可を流用しない。
- 承認待ちの内容、実行ID、有効期限、状態をバックエンドで保持する。LLMが生成する引数だけで承認済みと判断しない。
- 拒否・期限切れ・セッション終了では実行しない。承認の再送や重複イベントで二重実行しない。
- 実行後の取り消し可否と結果不明を区別し、結果不明の送信を自動再試行しない。
- 許可のUIはレベル0で必要最小限を用意する。レベル4まで外部操作の承認を先送りしない。
- ローカル検証では許可/拒否の状態遷移を自動テストし、実メール送信は必須にしない。

### Langfuseで監視する内容

| 単位 | 必要な情報 |
| --- | --- |
| セッション | session ID、ユーザー識別子、開始終了、リリース、プロンプト版 |
| 会話ターン | turn ID、入力から回答開始までの時間、完了/割り込み/エラー |
| モデル呼び出し | generation、モデル名、入出力使用量、費用、最初のトークンまでの時間 |
| ツール | 名前、選択・承認待ち・実行・終了、所要時間、成否 |
| 将来のMemory/RAG | 取得件数、参照ID、検索時間、失敗、回答への利用有無 |

traceとコストの表示は別々に検証する。モデル価格が一致しない場合は価格設定または明示的な費用記録を検討する。
LLM、STT、TTS、後続の埋め込み・検索等の費用は分け、実測値・単価による推計・取得不能を区別する。
Langfuse上の合計を請求額そのものと見なさず、サービス側の実績とも照合する。
会話・メール・記憶・文書の本文をどこまで外部トレースへ送るかは、実接続評価前に設定で明確にする。秘密情報は出力しない。

### 完了条件

- 実会話からtrace、generation、ツール実行まで追え、対応するセッションを特定できる。
- LLM使用量と費用が確認でき、その他の費用の算出範囲も分かる。
- 許可のない外部操作、拒否後の操作、重複承認による二重操作が行われない。
- 最大3文、不足情報への最初の確認、不明時の回答、自然な会話を評価できる。
- 同じ評価用会話でプロンプト変更前後の品質・遅延・費用を比較できる。

## レベル1: チャット形式の文字起こし

### 実装

- UI基盤は[assistant-ui](https://github.com/assistant-ui/assistant-ui)（React・TypeScript）とする。`fronted-test`内でReactを導入し、既存の起動・停止と音声接続を維持する。
- LiveKitの文字起こし・会話イベントをassistant-uiのメッセージへ変換するアダプターを実装する。独自状態を接続できる[ExternalStoreRuntime等のCustom Runtime](https://www.assistant-ui.com/docs/runtimes/custom/overview)を第一候補とし、採用APIは実装時のバージョンで確認する。
- assistant-uiを追加するだけでLiveKitと自動接続できるとは想定しない。LLMへの別経路の呼び出しや、ブラウザ側STT/TTSによる音声処理の二重化を避ける。
- ユーザーとAI双方の発言をチャット形式で表示する。
- 途中認識は同じ発言を更新し、確定発言を履歴にする。途中認識のたびに行を追加しない。
- AIの生成したテキストと、実際に読み上げたテキストを区別し、割り込みを反映する。
- session ID、turn ID、発言ID、話者、時刻、途中/確定/中断の状態を定める。
- 再接続時の重複・イベント順序・切断後に遅れて届くイベントを扱う。
- メモリ・RAG等の状態イベントの共通形式も定める。内容はレベル2以降で追加する。

### 完了条件

- 双方の会話が音声と対応し、途中認識で画面が重複しない。
- 割り込みで未発話の文章を発話済みと扱わない。
- 起動/停止/再接続で別セッションの内容が混ざらない。

## レベル2: PostgreSQLでのAgent Memory検証

### 2A: セッション内の文脈

LiveKitの会話履歴を先に検証し、同じセッションの直前の発言・訂正を踏まえて回答できることを確認する。
履歴が長い場合は要約と直近の発言を組み合わせ、コンテキスト量を制御する。

### 2B: セッションをまたぐ記憶

- PostgreSQLをローカルで起動し、会話原文・要約・長期記憶を分けて保存する。
- 長期記憶は好み・基本情報・継続中の話題を初期対象とし、会話中の全発言をそのまま事実として採用しない。
- 記憶の保存元、日時、ユーザー、更新・削除の状態を持たせる。
- 次のセッションでは関連する記憶だけを取得する。全文を毎回プロンプトへ挿入しない。
- 訂正・忘却の依頼を反映する。削除された記憶が再び検索・復元されないようにする。
- 誤った推測、仮定の話、他人についての話をユーザー本人の事実と取り違えない。
- ローカルDBが停止した場合、記憶機能の失敗を扱い、基本会話を継続できる設計とする。
- ユーザー識別はローカル検証用の安定IDから開始する。認証方式の本格化は別途検討する。

GCP Memory Bankへの移行はこの検証後に再設計する。現時点ではGCPとの完全なAPI・保存形式互換を求めない。

### 完了条件

- セッションAで保存した適切な記憶をセッションBで利用できる。
- 直近の訂正が反映され、削除した情報を使わない。
- 無関係な記憶や別ユーザーの情報を回答へ混ぜない。
- PostgreSQLの再起動後も保存内容が維持され、DB障害を追跡できる。

## レベル3: RAGとWeb検索

### 3A: ローカルMarkdown RAG

- ローカルの指定フォルダに置いたMarkdownだけを初期対象とする。
- 取り込み → 見出し等を使った分割 → 埋め込み → 索引保存 → 検索 → 回答生成を構築する。
- PostgreSQL＋pgvectorを初期候補とし、実装前に埋め込みモデル・次元・日本語検索品質を検証する。
- ファイル識別子、見出し、更新日時、チャンクIDなどを保持し、検索結果の出所を内部で追跡できるようにする。
- 追加・更新・削除を再索引へ反映し、同じ文書の重複取り込みを防ぐ。
- 検索結果が不十分なら、最初に一度必要な情報を人へ確認する。確認後も根拠がないことを作り話で補わない。
- 文書中の命令文をシステム命令として実行しない。
- 回答で出典を毎回読み上げたり第三者へ提示することは必須にしない。検証時には取得根拠を確認できるようにする。

Markdownでの成功後、自然言語を扱うファイル形式へ対象を広げる。PDF・Word等の順番、OCR、表の扱いは次の計画で決める。

### 3B: Web検索と将来のGCP活用

- Markdown RAGの評価後、外部ツールとしてWeb検索を追加する。
- Web検索の実行は人の許可後とし、結果はURL・取得日時・失敗を記録する。
- ローカル文書検索とWeb検索を区別し、最新情報の必要性に応じてLLMが選択する。
- 検索APIとページ取得の範囲、タイムアウト、検索回数・費用の上限を実装時に決める。
- 将来のGCP上の文書配置・検索サービス・Web検索フレームワークは、ローカル検証の結果から選定する。

### 完了条件

- 用意した質問に対して適切なMarkdownの箇所を取得できる。
- 文書の更新・削除後に古い内容へ依存しない。
- 資料にない質問へ根拠を捏造せず、3文以内の自然な回答を返せる。
- Web検索では許可/拒否、検索失敗、出所、取得日時を追える。

## レベル4: Memory・検索処理のストリーミング表示

### 実装

- レベル1で導入したassistant-uiを継続利用し、[Tool UI](https://www.assistant-ui.com/docs/tools/tool-ui)とカスタム表示でツールの進捗・結果・承認操作を表現する。
- LiveKit経由の処理イベントを、assistant-ui側の実行ID・表示状態に対応付ける。UIライブラリが通信・承認・実行を自動で保証するとは想定せず、バックエンドの実状態を表示する。
- 承認UIから許可/拒否を送る場合も、レベル0のバックエンド承認検証を必ず経由する。ツール実行やAPIキーをフロントエンドへ移さない。
- 「記憶を確認中」「文書を検索中」「取得内容を確認中」「Web検索中」「回答中」を実処理に対応して表示する。
- 承認待ち・拒否・完了・失敗・キャンセルも区別する。
- 内部思考を表示せず、開始/終了イベントと結果の状態を表示する。
- LiveKitのデータ通信を第一候補とし、送達・順序・再接続要件を確認して通知方式を決める。
- 共通イベントにsession ID、turn ID、実行ID、処理種別、状態、順序情報、時刻を持たせる。
- 並列処理・遅延イベント・重複・停止を扱い、完了した処理を「実行中」のまま残さない。
- 任意の詳細表示で検索先や記憶の利用を確認できるようにする。通常の会話表示を長いログで埋めない。

### 完了条件

- UIが実際のツール実行と一致し、検索していないのに検索中と表示しない。
- キャンセル・エラー・再接続でも表示が収束し、別のターンの進捗が混ざらない。
- ブラウザ表示とLangfuseの記録を共通IDで照合できる。
