# Care Support Voice Agent — 新人エンジニア向け専門用語集

本プロジェクト（Level 0 〜 Level 3A）の設計書・ソースコード・監視ログに登場する専門用語を、新人エンジニアの方でもイメージしやすいように整理しました。

---

## 1. リアルタイム音声・フロントエンド関連

### WebRTC
- **一言で**: ブラウザとサーバー（またはブラウザ同士）で音声・映像・データを超低遅延でやり取りする通信技術。
- **詳しい解説**: 通常の HTTP 通信のように「リクエストして返事を待つ」のではなく、双方向にリアルタイムでデータを流し続けられます。オンライン会議ツールでも使われています。
- **このシステムでの使われ方**: ブラウザのマイク音声をエージェントへ送り、エージェントの返答音声をブラウザで再生するために LiveKit 経由で利用しています。

### LiveKit / Room / Participant
- **一言で**: WebRTC を使ったリアルタイム音声・AI エージェント開発のためのプラットフォーム。
- **詳しい解説**: 「Room（部屋）」に人間（ブラウザ）と AI エージェントが「Participant（参加者）」として入室することで、音声やテキストをやり取りします。
- **このシステムでの使われ方**: ブラウザ（`fronted-test`）と Python 製エージェント（`Test-LiveKit/agent.py`）が LiveKit Cloud 上の Room を介して接続します。

### Token Server（トークンサーバー）
- **一言で**: ブラウザが LiveKit の Room に入るための「一時的な入場券（JWT トークン）」を発行する API サーバー。
- **詳しい解説**: LiveKit の秘密鍵（API Secret）をブラウザの JavaScript に埋め込むと漏洩してしまうため、サーバー側で安全な一時トークンだけを生成してブラウザに返します。
- **このシステムでの使われ方**: `Test-LiveKit/token_server.py`（FastAPI）が `/api/token` エンドポイントを提供しています。

### STT / TTS / VAD
- **一言で**: 音声会話の3要素。「音声→文字（STT）」「文字→音声（TTS）」「話している区間の検出（VAD）」。
- **詳しい解説**:
  - **STT（Speech-to-Text）**: ユーザーの話し声をテキストに変換する音声認識。
  - **TTS（Text-to-Speech）**: AI が作った文章を自然な音声に変換する音声合成。
  - **VAD（Voice Activity Detection）**: 「今ユーザーが話し始めた／話し終わった」を判定する仕組み。
- **このシステムでの使われ方**: 音声モード時のみ LiveKit Inference 経由で有効化し、テキスト専用セッション（`frontend-test-text-*`）では無効化してコストと遅延を抑えています。

### TTFT（Time To First Token）
- **一言で**: AI に質問を送ってから「最初の1文字目」が返ってくるまでの待ち時間。
- **詳しい解説**: 全体の回答時間よりも、人間が「反応が速い／遅い」と感じる体感速度に直結します。特に音声会話では TTFT を短くすることが重要です。
- **このシステムでの使われ方**: Langfuse トレースの `time_to_first_chunk` として計測し、応答速度の改善指標に使っています。

### RPC（Remote Procedure Call）
- **一言で**: ネットワーク越しに相手のプログラムの関数を直接呼び出す仕組み。
- **詳しい解説**: ブラウザからエージェント側の特定処理を呼び出し、結果を受け取れます。
- **このシステムでの使われ方**: ブラウザの承認 UI からエージェントの `approval.list`（承認待ち一覧取得）と `approval.decide`（許可／拒否の送信）を呼び出す際に使用しています。

### React / Vite / TypeScript
- **一言で**: モダンな Web フロントエンド開発の定番セット。
- **詳しい解説**: **React** は画面部品（コンポーネント）を作るライブラリ、**TypeScript** は型チェックでバグを防ぐ JavaScript の拡張言語、**Vite** は高速な開発サーバー＆ビルドツールです。
- **このシステムでの使われ方**: `fronted-test/` のブラウザ UI をこれらで構築しています。

### assistant-ui / Vercel AI SDK / AI Elements（ChainOfThought）
- **一言で**: AI チャット UI と、思考・検索ステップの開閉表示を作るためのライブラリ群。
- **詳しい解説**: Vercel AI SDK と assistant-ui でメッセージやストリーミング状態を管理し、Vercel 公式の **AI Elements**（`ChainOfThought` コンポーネント）で「今 AI が何をしているか（考え中・Web 検索中・ツール実行中など）」を折りたたみ可能なステップ一覧として表示できます。
- **このシステムでの使われ方**: Level 1 のチャット UI 基盤に加え、Level 4 で `@radix-ui/react-collapsible` と `lucide-react` ベースの `ChainOfThought` を導入し、リアルタイムの進捗ステータスを開閉表示しています。

## 2. AI・LLM・プロンプト関連

### LLM（Large Language Model / 大規模言語モデル）
- **一言で**: 人間のように文章を理解・生成できる AI モデル（GPT や Claude など）。
- **このシステムでの使われ方**: 会話の応答生成、ツールを使うかどうかの判断、会話からの長期記憶抽出（Extraction）と統合（Consolidation）に使用しています。

### OpenRouter
- **一言で**: 複数の会社の LLM（OpenAI、Anthropic、Google など）を共通の API 形式で呼び出せる中継サービス。
- **詳しい解説**: API キーや呼び出しコードを書き換えずに、環境変数（`OPENROUTER_MODEL`）を変えるだけでモデルを切り替えられます。
- **このシステムでの使われ方**: `openai.LLM.with_openrouter(...)` 経由で `openai/gpt-6-luna` に接続しています。

### Function Calling（Tool Use / `@function_tool`）
- **一言で**: LLM が外部のプログラム（ツール）を呼び出して結果を受け取る仕組み。
- **詳しい解説**: LLM 単体ではメールを読んだり DB を検索したりできませんが、関数をツールとして登録しておくと、LLM が必要な引数を選んで呼び出してくれます。
- **このシステムでの使われ方**: `search_emails` / `read_email` / `send_email`（Gmail）、`search_memories` / `list_recent_memories` / `save_memory`（記憶）、`search_documents`（RAG）、`search_web`（Tavily Web 検索）をツールとして提供しています。

### Tavily
- **一言で**: AI エージェント向けに設計された高精度な Web 検索 API。
- **詳しい解説**: 一般的な検索エンジンと異なり、LLM がそのまま扱いやすいタイトル・URL・要約テキスト（スニペット）・スコアを構造化 JSON で返してくれます。業界で広く利用されており検索品質が高いのが特徴です。
- **このシステムでの使われ方**: Level 3B として `Test-LiveKit/web_search_tools.py` に組み込み、ローカル文書に無い最新情報を調べる際に `ApprovalManager`（人間の承認）を経て呼び出します。

### System Prompt（システムプロンプト）
- **一言で**: AI にあらかじめ与えておく「役割・性格・ルール」の指示書。
- **詳しい解説**: ユーザーの質問より前に常に渡されるため、回答の長さや口調、ツールの使い分けルールを制御できます。
- **このシステムでの使われ方**: `Test-LiveKit/prompts/` で Git 版管理し、「最大3文」「不明時は推測しない」などの会話方針を定義しています。

### Prompt Caching（プロンプトキャッシュ） / `prompt_cache_key`
- **一言で**: 毎ターン同じ内容を送るシステムプロンプト等をサーバー側にキャッシュして、API 料金と待ち時間を減らす仕組み。
- **詳しい解説**: 会話が進むと毎回同じシステムプロンプトや過去の履歴を再送信することになります。キャッシュが効くと、繰り返し部分の入力トークン単価が大幅に安くなります。
- **このシステムでの使われ方**: `openai/gpt-6-luna` へのモデル変更と `prompt_cache_key` 設定により、自動キャッシュ（`prompt_cache_breakpoints='auto'`）を有効化しています。

### Reasoning Tokens（推論トークン）
- **一言で**: AI が最終回答を出力する前に「頭の中で考える」ために消費する内部トークン。
- **詳しい解説**: 複雑な問題では精度が上がりますが、トークン数が増えると料金が上がり、最初の回答が出るまでの時間（TTFT）も長くなります。
- **このシステムでの使われ方**: Langfuse トレースで `output_reasoning_tokens` を観測し、応答速度への影響を分析しています。

### Structured Output（構造化出力）
- **一言で**: LLM の出力を自由な文章ではなく、決まった形式の JSON に強制する技術。
- **詳しい解説**: プログラム側で確実にパースして DB に保存したい場合に使います。
- **このシステムでの使われ方**: 会話から長期記憶を抽出する際、JSON 形式で出力させて Pydantic で厳密にバリデーションしています。

## 3. 長期記憶（Agent Memory）・検索（RAG）関連

### Agent Memory（長期記憶）
- **一言で**: 1回の会話が終わっても、ユーザーの好みや習慣を次の会話まで覚えておく仕組み。
- **詳しい解説**: 通常の LLM はセッションを閉じると記憶が消えます。長期記憶を DB に保存し、必要なものだけ次回プロンプトに渡すことでパーソナライズが可能になります。
- **このシステムでの使われ方**: Level 2 として `Test-LiveKit/memory/` に実装し、セッション開始時の注入・会話中の検索/即時保存・終了時の自動抽出を行っています。

### RAG（Retrieval-Augmented Generation / 検索拡張生成）
- **一言で**: AI が回答を作る前に、外部の文書データベースから関連箇所を検索して参考資料として渡す手法。
- **詳しい解説**: LLM が学習していない社内規定やマニュアルの内容を、モデルを再学習させずに正確に答えさせることができます。
- **このシステムでの使われ方**: Level 3A として `Test-LiveKit/rag/` に実装し、`search_documents` ツール経由でローカル文書を検索します。

### Embedding（埋め込みベクトル）
- **一言で**: 文章の「意味」を数値の配列（ベクトル）に変換したもの。
- **詳しい解説**: 意味が似ている文章同士は、数値の配列（空間上の点）も近い位置に配置されます。これにより、単語が完全一致しなくても「意味が近い文章」を検索できます。
- **このシステムでの使われ方**: Ollama 上の `embeddinggemma-2:270m` を使い、テキストを 768 次元のベクトルに変換しています。

### pgvector / HNSW インデックス / コサイン類似度
- **一言で**: PostgreSQL でベクトル検索を高速に行うための拡張機能とアルゴリズム。
- **詳しい解説**:
  - **pgvector**: PostgreSQL に `vector` 型と類似検索演算子を追加する拡張機能。
  - **コサイン類似度**: 2つのベクトルの向きがどれだけ近いかを `0〜1` で表す指標。
  - **HNSW**: 大量のベクトルの中から近いものを高速に見つけるためのグラフ型インデックス。
- **このシステムでの使われ方**: `memories` テーブルと `rag_chunks` テーブルの 768 次元ベクトル検索に利用しています。

### Chunking（チャンク分割） / Corpus（コーパス）
- **一言で**: 長い文書を検索しやすい小さな塊（チャンク）に分けることと、文書の集合（コーパス）。
- **詳しい解説**: 数十ページの PDF をそのまま検索・プロンプト投入すると精度が落ちるため、数百文字ずつ少し重複（オーバーラップ）を持たせて分割します。
- **このシステムでの使われ方**: `RecursiveTextChunker` で日本語の句読点・改行を考慮して分割し、`corpus_id` ごとに文書を分類管理しています。

### Ollama
- **一言で**: 自分の PC（ローカル環境）で AI モデルを手軽に動かせるツール。
- **このシステムでの使われ方**: 外部 API 課金なしで高速に埋め込みベクトルを生成するため、`http://127.0.0.1:11434` で `embeddinggemma-2:270m` を稼働させています。

### Memory Consolidation（記憶の統合: ADD / UPDATE / DELETE / NOOP）
- **一言で**: 新しく抽出した記憶を、既存の記憶と突き合わせて整理する処理。
- **詳しい解説**:
  - **ADD**: 新しい記憶として追加
  - **UPDATE**: 既存の記憶を最新情報で上書き（例: 引っ越しや好みの変化）
  - **DELETE**: 忘却依頼や矛盾により削除
  - **NOOP**: すでに同じ記憶があるため何もしない
- **このシステムでの使われ方**: `memory/services/consolidation.py` が重複登録や古い情報の残留を防いでいます。

## 4. バックエンド・DB・非同期処理関連

### FastAPI / Uvicorn
- **一言で**: Python で高速な Web API を作るためのフレームワーク（FastAPI）と、それを動かすサーバー（Uvicorn）。
- **このシステムでの使われ方**: ローカルのトークン発行サーバー（`token_server.py`）で使用しています。

### `asyncio` / イベントループ（`ProactorEventLoop` と `SelectorEventLoop`）
- **一言で**: Python で「待ち時間のある処理（通信や DB アクセス）」を効率よく並行処理するための仕組み。
- **詳しい解説**: 1つのスレッドで複数の処理を切り替えながら動かします（この司令塔が **イベントループ**）。そのため、イベントループ上で重い同期処理をすると全体が一瞬止まります（`event_loop_blocked`）。Windows では標準が `ProactorEventLoop` ですが、`psycopg` 3 の非同期ドライバは `SelectorEventLoop` を要求します。
- **このシステムでの使われ方**: `agent.py` で Windows 時に `WindowsSelectorEventLoopPolicy()` を設定し、さらに `psycopg.types.net` を事前ロードしてブロッキングを防いでいます。

### SQLAlchemy（ORM） / `psycopg` 3 / Alembic
- **一言で**: Python から PostgreSQL を安全・効率的に扱うための3点セット。
- **詳しい解説**:
  - **SQLAlchemy**: SQL 文を直接書く代わりに Python のクラスで DB 操作できるツール（ORM）。
  - **psycopg 3**: Python と PostgreSQL をつなぐ最新の通信ドライバ。
  - **Alembic**: テーブルの作成・変更履歴をコードで管理するマイグレーションツール。
- **このシステムでの使われ方**: `database/` と `migrations/versions/` でメモリ用・RAG 用テーブルを管理しています。

### Pydantic
- **一言で**: Python のデータ型チェックとバリデーション（入力検証）を自動で行うライブラリ。
- **このシステムでの使われ方**: メモリや RAG のデータモデル定義、および LLM の JSON 出力検証に使っています。

### `uv`
- **一言で**: Rust 製の超高速な Python パッケージ・仮想環境管理ツール。
- **このシステムでの使われ方**: `Test-LiveKit/` の依存関係管理（`pyproject.toml` / `uv.lock`）とコマンド実行（`uv run`）に使用しています。

## 5. セキュリティ・運用・監視（オブザーバビリティ）関連

### Human-in-the-Loop（HITL / 承認フロー）
- **一言で**: AI にすべてを自動実行させず、重要な判断や外部操作の前に「人間の確認・承認」を挟む安全設計。
- **このシステムでの使われ方**: Gmail の検索・読み取り・送信はすべて `ApprovalManager`（`approvals.py`）で一時停止し、ブラウザ UI で人間が「許可」を押したときだけ実行します。

### OAuth 2.0
- **一言で**: パスワードを直接渡さずに、外部サービス（Google など）への限られたアクセス権限だけを安全に許可する認証の仕組み。
- **このシステムでの使われ方**: `gmail_auth.py` でユーザーの Gmail 読み取り・送信権限のトークンを取得・管理しています。

### PII（Personally Identifiable Information / 個人情報）と Redaction（マスキング）
- **一言で**: 氏名・メールアドレス・会話内容など個人を特定できる情報（PII）を、外部ログへ送らないように伏せる処理（Redaction）。
- **このシステムでの使われ方**: デフォルトで `LANGFUSE_ALLOW_PII=false`（`content_policy: redacted`）とし、Langfuse にはメタデータ（遅延・トークン数・成否）のみを送る設計にしています。

### OpenTelemetry（OTel） / Trace / Span / Generation / OTLP
- **一言で**: アプリケーション内部の動きを記録・可視化するための標準規格とデータ単位。
- **詳しい解説**:
  - **Trace（トレース）**: 1回のセッション全体の処理のまとまり。
  - **Span（スパン）**: トレースの中の個別の処理（DB 検索、ツール実行など）と所要時間。
  - **Generation（ジェネレーション）**: スパンのうち、特に LLM 呼び出し（モデル名・トークン数・コスト）を表すもの。
  - **OTLP**: トレースデータを外部監視ツールへ送るための標準通信プロトコル。
- **このシステムでの使われ方**: LiveKit と自作コードから OpenTelemetry スパンを発行し、`ReportingExporter` で整形して Langfuse へ送信しています。

### Langfuse
- **一言で**: LLM アプリ専用のオブザーバビリティ（監視・分析・評価）プラットフォーム。
- **詳しい解説**: 会話ごとの処理ツリー、TTFT、トークン消費量、推定コスト、エラー箇所を画面や API で追跡できます。
- **このシステムでの使われ方**: 実会話のボトルネックやバグ（DB エラー、承認期限切れ、コスト未計上など）を発見・改善するための根拠データとして活用し、TEST-秘書モードでは DeepEval の採点スコア登録先としても使用しています。

### DeepEval（GEval / ConversationalGEval）
- **一言で**: LLM の回答品質を別の LLM（Judge）で自動採点する評価フレームワーク。
- **詳しい解説**: `GEval` は単発の最終回答が期待内容を満たしているかを採点し、`ConversationalGEval` は複数ターンの会話の流れ（途中の言い直し・訂正への追従など）を採点します。
- **このシステムでの使われ方**: TEST-秘書モードのテスト通話を `evaluations/evaluate_secretary.py` から手動採点し、結果を CLI 表示と Langfuse のスコア登録に利用しています。

### JWT メタデータ認証
- **一言で**: サーバーが署名したトークン（JWT）の内部に、改ざんできない本人情報を埋め込む仕組み。
- **詳しい解説**: ブラウザが送ってくる自己申告の ID ではなく、サーバー側で DB 照合した社員 ID を署名済み JWT に載せることで、クライアント側の成りすましを防ぎます。
- **このシステムでの使われ方**: `token_server.py` が PostgreSQL で社員を照合したうえで LiveKit トークンの `metadata` に `employee_id` を埋め込み、`agent.py` はその値だけを参照して予定・タスクを取得します。

### グレースフルフォールバック（Graceful Fallback）
- **一言で**: 一部の機能（DB や外部 API）が障害で落ちても、システム全体をクラッシュさせず最低限の動作を継続する設計。
- **このシステムでの使われ方**: PostgreSQL が停止していても、メモリ・RAG ツールがエラーメッセージを安全に返し、通常の音声・テキスト会話はそのまま続けられます。

### Cloudflare Workers / Containers
- **一言で**: エッジ環境で高速に動くサーバーレス実行基盤（Workers）と、常駐コンテナを動かせる基盤（Containers）。
- **このシステムでの使われ方**: 将来のクラウド公開用に、ブラウザ UI＆トークン発行を Workers、Python エージェントを Containers で動かす構成（`wrangler.jsonc` / `Dockerfile`）を整備しています。

### Next.js / Recharts

- **一言で**: Next.js は React で Web アプリを構築するフレームワークです。Recharts は React 用のグラフライブラリです。
- **詳しい解説**: Next.js の App Router はファイル構成から画面ルートを定義します。Recharts は配列データから折れ線や円グラフを描画します。
- **このシステムでの使われ方**: `evaluation-web/` で管理画面のルートを定義し、合成の評価推移と安全性テスト件数を表示します。

### アノテーション

- **一言で**: 評価対象に結び付けるコメントやラベルです。
- **詳しい解説**: 人が確認した根拠や分類を記録し、評価の見直しに使います。
- **このシステムでの使われ方**: セッション詳細モックで既存ラベルの表示とコメント入力を確認できます。

### 末端スパン

- **一言で**: 子スパンを持たない処理の計測単位です。
- **詳しい解説**: 親の合計値に子の計測値が含まれる場合、両方を加算すると重複します。
- **このシステムでの使われ方**: トレース詳細モックのコスト小計は末端スパンの計測値を足し、未計測件数を併記します。

### 設定ドラフト

- **一言で**: 適用前の設定を編集するための下書きです。
- **詳しい解説**: アクティブ版の内容を引き継ぎ、変更点を確認してから適用判断に進みます。
- **このシステムでの使われ方**: Agent 基本設定モックでは、基本項目とタグを編集し、サンプルの履歴と比較できます。

### Temperature / Top-p

- **一言で**: LLM が次のトークンを選ぶときの候補の選び方を調整するパラメーターです。
- **詳しい解説**: Temperature は候補の確率分布の偏りを調整し、Top-p は合計確率が指定値に達するまでの候補に選択範囲を絞ります。
- **このシステムでの使われ方**: LLM 設定モックでドラフトを編集し、現在の値と比較できます。

### P95 実行時間

- **一言で**: 計測した処理時間のうち約95%が収まる値です。
- **詳しい解説**: 最近順位法では、計測値を昇順に並べ、件数に0.95を掛けて切り上げた順位の値を使います。
- **このシステムでの使われ方**: 評価モニタリングで終了済み Run の計測値を集計し、母数を併記します。
